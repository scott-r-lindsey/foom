Keep the work moving. See when it needs you.

    So the core idea of Foom is that you spin up a top-tier model to be your orchestrator, and it manages as many mid-tier agents as you have tokens to spend. Every agent is connected to an MCP server that lets agents send messages to and receive messages from each other, and the agents are divided into orchestrators, workers and reviewers.

    Getting started

    Foom is a desktop board for local coding agents and shells. It groups sessions by Git repository and worktree, displays their terminals in tiles, and marks the sessions that need your attention. Your agents remain their own command-line programs, with their own accounts and permissions.

    First-run setup walks through Agents, Repositories and Go / no-go. Install Git and the agent CLIs you want to use, then recheck discovery. Launch requires Git, at least one ready agent and one added repository. Choose which detected agents to enable, select repositories, and review readiness before continuing. The evaluator classifies attention locally.

    This manual opens after setup completes. Close its tile when you are ready. Open Help → Manual from the foom wordmark menu at any time; macOS also has Help in the native menu bar. Reopening selects the existing manual tile. The bundled guide works offline and follows the light or dark appearance.

    Agents can read this manual. Sessions launched with Foom MCP can call manual to list sections and read them on demand. Config agents with per-launch MCP support receive only this read-only tool.

    The packaged app and Foom Dev use separate profiles. Windows, repositories and preferences in one profile do not automatically appear in the other.

    Repositories and worktrees

    Use Add repository in the wordmark menu or the + Add repo row in the sidebar to select a local Git repository. Adding registers it with Foom; it does not start a session. The sidebar shows its main checkout and linked worktrees, including worktrees created outside Foom.

    A worktree is a separate checkout of the same repository. Use one per task when agents need independent files and branches. A worktree is not a sandbox: a program running there still has your operating-system account's access.

    Create a worktree

    Open the repository panel and choose New worktree. Type a branch name; spaces become hyphens. Tab accepts the ghost completion, and Up/Down cycle suggestions. The status line tells you whether Enter creates a branch from the repository's current HEAD, checks out an existing branch, tracks an origin branch, or selects a worktree that already has that branch. Escape returns to the panel. Creation starts no agent or shell.

    Settings controls whether new worktrees live under Foom's worktree root or next to your repositories. Foom validates destinations and refuses to overwrite an existing directory. Open the new worktree's panel to launch a session.

    Remove or forget

    Remove from Foom… forgets a repository registration and keeps its files. Tracked sessions or pending operations can prevent forgetting it. Delete worktree… removes a linked checkout, is unavailable while a session runs there, and reviews uncommitted changes before discarding them. Ordinary worktree deletion keeps the local branch. The main checkout cannot be deleted through this action.

    Delete merged worktrees checks the remote default branch with a fresh fetch and presents eligible and retained checkouts. Running sessions, changed files, locks and resumable exited conversations can retain a checkout. Approving deletion rechecks the evidence. Stop finishes removals in flight; Hide closes the progress window while work continues. Merged cleanup can also remove a local branch when it still points to the checked commit. A failed fetch prevents cleanup.

    Agents and shells

    Click a checkout name to open its panel, then choose an enabled agent or Shell. A repository can have several sessions in the same checkout; Foom asks before launching another agent beside a running agent there. Multiple agents in one checkout share files.

    The home shell row above repositories launches a shell in your home directory. Checkout shells start in that checkout. Shells use the All sessions environment settings; agents additionally use their own settings.

    Click a session row or press Enter to place its terminal and focus input. Hovering or focusing a row alone leaves your terminal unchanged. Double-click a session name to rename it; Enter or blur saves, Escape cancels, and an empty name restores the default. The full agent or shell identity remains available in the panel.

    Resume a conversation

    Choose Resume conversation… in the checkout panel. Paste a supported resume command such as claude --resume <id>, codex resume <id> or agy --conversation <id>, or paste a bare ID and choose the detected agent. The available picker choices use the CLI's own conversation picker. Close the conversation elsewhere before resuming it here. Foom does not read your agent transcript files.

    Hide, stop and restore

    Hide removes a running terminal from its tile while its process continues. Stop in the session panel ends the process. An exited terminal retains its final screen until you Close its session. Restart uses a new process. Closing a tile never stops a running terminal.

    With Restore sessions on launch enabled, sessions that were running at quit restart on the next launch. Exited sessions remain exited, and known conversation IDs can support agent resume. Terminal screens and scrollback are not saved across app restarts. Quit reviews running terminals and stops them after confirmation.

    Tiles and windows

    Each occupied tile contains one terminal or preview and has a numbered menu in its title bar. Split right and Split down create empty space, preserve your terminal focus, and make the new space the next landing spot. Showing a hidden session fills that spot, then other empty space.

    A full board normally adds a column at the far right. If columns would become too narrow, Foom replaces a least recently focused tile that does not need you; its terminal keeps running hidden. When every tile needs attention, Foom can add a narrower column. Layout resource limits still apply.

    Drag a sidebar session onto a tile's center to replace its content, or onto an edge to split. Drag a tile title bar onto another tile's center to swap tiles, or onto an edge to move it. The drop outline names the destination. Escape cancels.

    Drag gutters to resize. With a gutter focused, arrow keys resize it and Home/End choose its limits. Double-click a gutter or press Enter to even the adjacent run. Grow absorbs neighboring empty space; it is unavailable beside occupied content. View → Tidy tiles removes empty space and evens the layout while keeping tile order.

    Maximize expands a tile temporarily; Restore returns to the split layout. Double-clicking its title bar does the same. Layout, sidebar width and collapse choice are remembered per window. Maximize is temporary.

    New window opens another board. Move to new window transfers a terminal or preview when available. A session's live terminal belongs to one window at a time. Closing a macOS window keeps the app running; closing the last window on Windows or Linux requests quit.

    Sidebar and attention

    The sidebar groups repository → worktree → session. Chevrons expand groups; clicking a checkout name opens its commands and facts. Pin repositories to keep them at the top. The filter matches repository, branch, session name and reason. If filtering hides sessions that need you, its banner offers Show to clear the filter.

    Use a row's ⋯ button, right-click or Shift+F10 to pin its command panel. Arrow keys, Home/End and Enter navigate commands. Escape closes it and returns focus to the row. Hover panels open after a short delay; they do not replace a pinned panel.

    StateMeaning
    WorkingThe agent is active; violet indicates activity.
    Needs youA question, permission prompt or other detected input need. Amber and a steady halo draw attention; read the reason and terminal.
    DoneThe agent's current work is complete.
    FailedA failure, shown with magenta and a square light.
    QuietNo current attention signal.
    WaitingAn idle orchestrator is waiting on its children; its count is separate from a question for you.

    Solid lights represent running processes; hollow rings (square outlines for failures) represent exited ones. Working agents and running shells can glow with output. Shells otherwise stay neutral, except when they need you. Text, shapes and the halo accompany color.

    The longest-waiting command selects the oldest waiting session. Opening a Needs you session does not dismiss its classification. Reply through its terminal. If the classification is wrong, choose Dismiss; failed feedback remains available to retry. Done and Failed dim after you see them.

    Collapse the sidebar to keep its lights in a compact rail, or drag its border to resize the expanded tree. Below 720 CSS pixels the rail is automatic, with an overlay tree when opened. The footer offers interface size, volume and the Foom config gear.

    Previews

    Choose Preview file… in a checkout panel and select a Markdown or HTML file inside that checkout. Hidden files, unsupported types and files outside it are refused. Relative assets must stay within the captured checkout root. Agents launched by Foom can also open previews in their own worktree.

    If a moved preview has no tile bounds after five seconds, it appears in a default landing area. Closing its new window before the preview appears returns it to the original window. If that window has closed or reached its preview limit, Foom opens a replacement board.

    Markdown supports headings, tables, task lists and highlighted code. Raw HTML stays text, and Mermaid fences stay code. Relative Markdown links navigate inside the tile. Files reload when their watched contents change, preserving scroll position when possible. A missing document waits for the file to reappear.

    A preview has its own isolated browser session, no Foom bridge and no Node access. Network access starts Off. Allow network… asks before enabling HTTPS and secure WebSockets for that preview. The page can then send readable checkout files to the internet. Permission resets on restart or when moved to another window. Plain HTTP connections remain blocked.

    External links ask in a trusted Foom dialog showing the full URL before opening your browser. Declining opens nothing. Preview menus and panels show a frozen page image while they cover the live view. Foom shortcuts remain available inside previews.

    Ordinary previews do not take keyboard focus on open or reload. Click the page to interact. Close ends the preview; it has no process to hide. Agent-opened previews identify their opener outside the page. Closing one sticks: reopening by that agent leaves a sidebar row until you choose to show it.

    The manual uses this same contained preview path with a bundled, read-only root. It has no network permission and is not copied into your repositories or profile.

    Settings and providers

    Open Settings from the wordmark menu, the config gear panel or its keyboard shortcut. It opens on General. General’s Show repository paths relative to code folder toggle is off by default; enable it to show nested names such as work/foom in the sidebar. Repositories outside the code folder keep their names. Settings stays beside the sidebar; returning to the board restores the terminal views. Preferences apply according to their scope: appearance updates the app, while new launch arguments and environment values apply to future sessions.

    • General: session restoration, worktree location and orchestration preferences, including the concurrent child limit and unread child reminder.
    • Terminal: font family, size and cursor.
    • Themes: interface themes and terminal palettes, with previews.
    • Forges: enabled forge providers, assigned hosts and readiness.
    • Appearance: System/Light/Dark, interface size and panel color. System follows the operating system's light/dark choice. Foom respects your system's reduced-motion preference.
    • Sound: master, working and alert volumes and sound choices. The footer speaker mutes; moving its volume slider unmutes.
    • Agents: discovered providers, enabled state, attention and hook capabilities, default arguments and provider settings. Discovery and version capabilities determine which integrations are available.
    • Environment: variables for All sessions; per-agent lists are in Agents. Values are literal, not shell expressions; PATH prepends absolute directories. Reserved or unsafe names are refused. Secret values use OS-backed encryption and are masked after saving. Existing sessions keep their original environment.
    • Foom config: the local configuration folder, validation and held changes. The gear's panel also offers agents and a shell in that folder.

    Use Via Claude Code or another enabled agent in the sidebar’s Foom config gear panel to start a session in the Foom config folder. An agent can help edit configuration there. Invalid files are rejected; changes that require review stay held until you decide. Do not assume that editing a file has applied it: inspect the config status.

    Provider manifests define discovery, launch and integration capabilities. Use the config workflow to add or adjust providers and inspect validation failures. Launch arguments that bypass an agent's safety checks require a disclosure before being saved as defaults; a Bypass label records known flags for that launch. It does not infer every global agent policy.

    Antigravity's lifecycle plugin is an explicit opt-in in Settings. Foom does not silently install it. Config-owned probes run real agent CLIs in temporary scratch repositories, can use credits, and can be stopped. A probe's driver can read that probe's visible screen for verification; it cannot read unrelated sessions through that capability.

    Forges and checks

    Foom can show pull or merge request metadata through enabled forge providers and explicitly assigned hosts. The bundled GitHub provider uses your installed gh CLI; GitLab uses glab. Both use existing CLI logins. GitHub rows show #N; GitLab rows show !N and head-pipeline status. A blocked manual pipeline is pending; a skipped pipeline or explicit no-pipeline result has no checks. Assign self-hosted GitLab hosts in Settings → Forges. Foom reads status; it stores no forge tokens, changes no CLI login and writes nothing to the forge.

    Checkout rows show a matched PR number and check status. Open the number to view it in your browser; the checkout panel shows its title and check counts. Running checks stay neutral, passed checks are green and failures magenta. Missing or logged-out CLIs, unknown remotes and ambiguous matches can leave status absent.

    Settings controls board PR display; orchestrator tracking is separate. Foom polls status, slows settled or failing reads, and pauses during sleep or screen lock. Completion notifications honor the sound-alert and mute preferences. A passed check notification is suppressed while an agent in that checkout is working.

    Orchestrators and children

    Open a running agent's session panel and choose Make orchestrator…. Review the disclosure. One session per repository holds the role; granting it to another revokes the first. Tell the agent when you grant it. Revoke orchestrator removes the role without restarting the session.

    An orchestrator can create worktrees, launch children within its repository and configured concurrent limit, prompt them, send keys and stop them. It can send input even at permission or credential prompts. Children cannot orchestrate through Foom and do not inherit the parent's launch flags. The default concurrent child limit is four; Settings → General accepts 1–16.

    Children appear under their own checkouts with a child mark and parent context. Settings → General → Show new children on the board is on by default; turn it off to keep new children in the sidebar until you open them. Existing tiles and restored children keep their placement. Selecting or hovering the parent highlights related children. Take over ends the orchestrator's access to that child so you can direct it yourself. Parent exit or role revocation also ends authority. Worktrees do not isolate processes running under your account.

    Foom supplies eligible agents with per-launch MCP and a foom console on their local PATH. MCP capability depends on the provider, version and policy; Antigravity uses the console for orchestration. Ordinary agents have scoped metadata and preview capabilities, while orchestration mutations require the role. The panel reports MCP connection status.

    A child reports Done, Blocked or Failed with a handoff summary and optional HTTPS links. The parent pulls reports; Foom never types them into its terminal. The child's panel shows the latest report. An unread child event can raise Child report unread on the parent after the configured reminder (five minutes by default; zero turns it off). Focusing the parent acknowledges those reminders without dismissing its own input need.

    The orchestrator can read bounded child terminal tails with likely secrets redacted, and child-authored reports. These may enter the orchestrator agent's model context. Redaction cannot catch every secret. Removal of a worktree requests human confirmation unless the explicit Auto-remove merged worktrees setting permits a clean, verified merged checkout. That setting starts off.

    Developer → Action log opens local history with search and action/outcome filters. It records actors, targets, outcomes and hashes of child input, rather than the input text or terminal tails. Clear history asks for a second click. History retains up to 30 days in at most five 10 MiB files.

    Keyboard shortcuts

    These tables come from the same command registry as the menus. Commands act on the focused window and are available only when their action applies. On Windows/Linux, release Ctrl+Shift+Space, then press the next key within two seconds for a tile-leader shortcut. Escape, blur or an unmatched key cancels the leader. Plain terminal control keys remain terminal input.

    Alt alone or F10 opens the in-window menu on Windows/Linux. Arrow keys navigate menus and sidebar commands; Enter activates and Escape dismisses. Keyboard shortcuts in the wordmark menu opens the app's compact shortcut sheet.

    Privacy and permissions

    Foom classifies terminal attention locally and sends no terminal content to a model or network service itself. Your agent CLI still communicates with its own model provider under its own account and settings.

    Two explicit capabilities can place output into an agent's context: an orchestrator can pull its children's redacted terminal tails and handoffs, and a config agent can read the visible screen of a probe it owns. Those agents may send the results to their providers. Ordinary session metadata tools do not return terminal output.

    Agent configuration is attached per launch rather than installed into global agent configuration or written into your repository. The opt-in Antigravity lifecycle plugin is the disclosed installation exception. Environment secrets are encrypted with Electron safeStorage; if suitable OS encryption is unavailable, saving secrets is refused.

    Preview pages are isolated and network-blocked unless you explicitly allow their secure network access. Read the full external-link or network disclosure before accepting. The bundled manual stays offline. Orchestrator roles, pairing and worktree removal use trusted Foom confirmations. A worktree, a probe's working directory and a child role are not operating-system sandboxes.

    Troubleshooting

    Git is unavailable
    Install Git so the app can discover its executable, then recheck Go / no-go. Setup cannot complete until Git is ready.
    An agent is missing or disabled
    Inspect Settings → Agents, refresh discovery and check the CLI installation. Unix discovery uses a login-shell PATH. On Windows, wrappers that require a batch or PowerShell command shell need a native executable on PATH. Version or help-flag checks can leave hooks or MCP unavailable even when terminal launch works.
    A session says Needs you, but it does not need input
    Read its terminal and reason, then use Dismiss for an incorrect classification. Opening the session alone does not clear Needs you. The evaluator is local and provider-specific signals can be incomplete.
    A session disappeared from the board
    Look in the sidebar: hiding or replacing a terminal tile keeps the session running. Select it to show it again. Clear the filter if it is hiding the row.
    A worktree was removed outside Foom
    Its existing sessions stay available with Worktree removed. Stop or close them; launches and restarts there are unavailable. The row disappears after its last session closes.
    A preview is blank or says File not found
    Check that its document and relative assets exist inside the selected checkout and are not hidden or symlinked outside it. Missing files recover when they appear. Network resources are blocked by default. Ordinary HTML page navigation is restricted; Markdown links can navigate within the tile.
    PR or CI status is absent
    Check the enabled forge, assigned host and your forge CLI's existing login. Unknown remotes, unavailable results and ambiguous branch matches leave no status rather than a guessed PR.
    A child is blocked or its report is unread
    Inspect the child panel and terminal. Let the parent pull its report, focus the parent to acknowledge reminders, or take over the child. An unread reminder and the parent's own permission prompt are different attention sources.
    A configuration change has not applied
    Inspect Foom config's rejected-file or held-change status. Correct validation errors or review the held change. New environment values and default launch arguments affect future sessions, not running ones.
    Scrollback is gone after restarting Foom
    Foom retains session records and eligible resumes, not terminal screens or scrollback. Keep durable results in your project or agent's own supported conversation storage.
